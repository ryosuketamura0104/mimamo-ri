# ADR-0001: 生存検知の多層シグナル + 2段階エスカレーション設計

## ステータス
承認 (2026-07-08)

## コンテキスト

本アプリの核心価値は「一人暮らしの人がスマホを使っていない状態が続いたら見守る側に通知する」こと。この検知が成立しないならアプリを作る意味がない。

前提として「**端末の生存**（電源・通信あり）」と「**人の生存**（本人がスマホを操作した/動いた）」は別物。端末は充電器の上で応答し続けるため、端末生存の確認だけでは人の異常を検知できない。

### iOSの制約（調査済み）

- **Widgetの表示イベントは取得不可能**。WidgetKitはタイムライン方式で、`getTimeline` が動くのはOSが決めた更新タイミングであり、ロック中でも更新が走る。「Widget更新＝人が見た」は誤り。ただし更新予算はユーザーの利用時間帯に偏って配分される
- **スクリーンタイム系**: `DeviceActivityMonitor` はアプリ/カテゴリ/Webドメインの使用時間しきい値イベントのみ取得可能。拡張はネットワーク不可・RAM約6MBだがApp Group書き込みは可能。しきい値は「スケジュール区間開始からの累積」で計算され、イベントは**区間ごとに1回のみ**発火（Apple engineer明言）。区間は最短15分。しきい値の公式な最小値はなく、秒単位は動作報告なし（15分なら安全と判断）。シミュレータ不可・実機検証必須。`DeviceActivityReport` のロック解除回数等は表示専用サンドボックスでApp Group書き込みも不可＝シグナル源に使えない。配布にはFamilyControlsエンタイトルメント申請が必要
- **ロック解除イベント**の常時監視は不可（アプリはすぐサスペンドされる）。ただし `FileProtectionComplete` ファイルの読み取り試行（保護ファイルプローブ）で「その瞬間解除中か」は任意の拡張から判定できる
- **通知フィルタリングエンタイトルメント**（表示なしでNSE実行）は対象ユースケースが限定されており見守り用途は却下リスク大 → `interruption-level: passive` で代替
- **ロケーションプッシュ**（CLLocationPushServiceExtension）: 通知を表示せず拡張を起動し位置取得・API送信が可能。アプリ強制終了時も動く。要エンタイトルメント申請だが「位置情報共有機能を持つアプリ」が正面の対象（SOS機能を持つ本アプリは該当見込み）。ユーザーの「常に許可」が必要
- **ショートカット個人オートメーション**: アラーム停止・特定アプリ起動・充電接続等をトリガーにApp Intentをバックグラウンド実行できる（iOS 17+「すぐに実行」）。ただしプログラムから設置不可・ユーザーの手動設定が必要で強制力なし
- Appleの「非使用のAppを取り除く」（オフロード）はWidget設置でも防げる保証がない

### 数値検証（iOSパッシブシグナルの捕捉率）

- ロック解除サンプリング: 高齢者の解除状態は1日の2〜4%程度。毎時ping（24回/日）での捕捉期待値は**0.5〜1回/日** → 元気でも観測ゼロの日が頻発し、単独では誤報だらけで不成立
- 歩数（CMPedometer）: ハードが常時記録し過去7日を照会可能でサンプリング欠落なし。ただし**家でスマホを持ち歩かない人は在宅日0歩** → 単独では誤報
- 結論: **パッシブシグナルの論理和でも「元気だが静かな日」を救えず、完全パッシブ検知は誤報率が実用レベルに収まらない**

### Android

`UsageStatsManager`/`UsageEvents` で画面ON・ロック解除の履歴そのものが取得できるため問題なし。1日数回の同期で欠落なく判定可能。

## 検討した選択肢

1. **完全パッシブ検知（シグナルのみで判定）**: UX最高だが上記の通りiOSでは数値的に不成立。誤報多発で信頼を失う
2. **毎日の能動チェックイン（朝ボタンを押す等）のみ**: 確実だが「毎日何もしなくていい」という価値を毀損。押し忘れ誤報も多い
3. **パッシブ多層 + 途絶時のみ2段階エスカレーション**: 普段は何もさせず、シグナルが途絶えた時だけ本人確認 → 無応答で初めて見守る側に通知

## 決定

選択肢3を採用。

```
パッシブシグナル（下記いずれか）が T時間（既定12h、設定可能）ゼロ
  → 見守られる側本人に確認通知「元気ですか？タップしてください」（音あり）
  → 1時間以内にタップなし
  → 見守る側にアラート（最終シグナル時刻・最終位置つき）
```

### iOSシグナル層（あるだけ使う多層構成）

| # | シグナル | 種別 | 頻度/粒度 |
|---|---------|------|----------|
| 1 | ロケーションプッシュ毎時ping（応答=端末生存+位置、同時に保護ファイルプローブでロック状態） | 端末+人(弱) | 毎時 |
| 2 | DeviceActivityMonitor: 全カテゴリ「累積15分使用」イベント → App Group記録 → ping時に報告 | 人(強) | 6時間毎区間×1回=最大4回/日 |
| 3 | CMPedometer歩数履歴（ping時に照会） | 人(中) | 連続記録・欠落なし |
| 4 | Widget `getTimeline` 内の保護ファイルプローブ（利用時間帯に偏るサンプラーとして活用。保証層にはしない） | 人(弱) | 40〜70回/日・OS任せ |
| 5 | ショートカットオートメーション（アラーム停止・アプリ起動→App Intentで即時報告）。設定してくれた人向けの精度ブースト | 人(最強) | 行動の度 |
| 6 | NSE（天気/メッセージ通知受信時の報告）+ passive通知 | 端末 | 配信の度 |

### ユーザー設定（見守る側が設定、見守られる側の端末に同期）

- **区間の刻み**: DeviceActivityScheduleの区間長を選択可能（例: 4/6/8/12時間）。刻みがシグナルの最大頻度を決める
- **静穏時間帯（夜間除外）**: 例 22:00〜7:00 の間は途絶タイマーを進めず、本人確認通知・アラートも発火しない。途絶判定は「アクティブ時間帯の累積無シグナル時間 ≥ T」で計算する
  - トレードオフ: 静穏時間帯中の異常は「静穏明け + T」まで検知が遅れる（仕様として明示する）
  - 睡眠中の無シグナル8時間が誤報の最大要因のため、この設定は既定で有効にする

### Androidシグナル層

- UsageStatsManagerの利用履歴を定期同期（WorkManager）+ FCM高優先度データメッセージでの補助起床

## 理由

- **誤報** = 「T時間偶然無シグナル」∧「確認通知も無視」の同時確率まで下がり実用レベル
- **見逃し** = 倒れている本人は確認タップできないため構造的にほぼ発生しない（フェイルセーフ: 途絶＝通知側に倒す）
- 検知遅延 = T + 1時間（T=12hで最悪13時間）。孤独死見守りの商用サービスの標準（12〜24h）と同水準
- プロダクトの約束は「普段は何もしなくていい（確認通知はシグナル途絶時だけ）」であり「一切何もしなくていい」ではない、と価値定義を明確化

## 影響

- サーバーは全シグナルを `signals` テーブルに集約し、cronで途絶判定 + エスカレーション状態機械（正常→本人確認中→アラート）を回す
- iOSはApp本体 + 4つの拡張（Widget/LocationPush/NSE/DeviceActivityMonitor）+ App Intents構成になる
- エンタイトルメント申請2件（location.push、family-controls）をリリース計画に織り込む。申請が通るまでの生存確認はpassive通知+NSE等で代替
- オンボーディングで必須: 通知許可、位置情報「常に許可」、FamilyControls承認、オフロードOFF案内、（任意）ショートカット設定ガイド
- **実装前の必須スパイク**: DeviceActivityMonitorの実機検証（しきい値15分/1分の発火挙動、区間跨ぎ、低電力モード・再起動後の継続性、6MB制限下のApp Group書き込み）
